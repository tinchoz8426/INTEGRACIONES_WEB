TURNOSRED
Backend de Gestión de Turnos Médicos
Documento de Evidencia • Pruebas API REST • Node.js / Express / Socket.IO / Zod

1. Alcance y Objetivo

El presente documento recopila la evidencia de las pruebas realizadas sobre la API REST TurnosRed (Node.js, TypeScript, Express y Socket.IO). Se documenta la ejecución de peticiones en el cliente Thunder Client (VS Code), la validación Zod con errores 400 estandarizados, las consultas con query params, la ejecución de tests automatizados en estado Pass y la simulación de la API mediante un Mock Server local (json-server).

Tecnologías: Express 5 • Socket.IO 4 • Zod • TypeScript 6 • Postman / Newman.

2. Configuración previa para las evidencias

2.1 Servidor local

  • Ejecutar el backend: npm run dev (puerto 3000).
  • Verificar en consola: "Servidor de TurnosRed ejecutándose en el puerto 3000".

2.2 Cliente de pruebas (Thunder Client)

  • Abrir la extensión Thunder Client en VS Code (icono de rayo en la barra lateral).
  • Crear una colección "TurnosRed" y usar la base http://localhost:3000.
  • Los scripts de test automatizados se ejecutan con Newman sobre la colección postman/TurnosRed.postman_collection.json.

2.3 Preparar el Mock Server (json-server)

  • Levantar el mock local con: npx json-server postman/mock-db.json --port 3001
  • Los datos ya están normalizados en postman/mock-db.json (formato objeto con rutas /turnos y /medicos).

3. Evidencia de peticiones y respuestas

Se muestran las respuestas reales obtenidas (formato JSON) mediante Thunder Client.

4. Evidencia de validaciones Zod (error 400 estandarizado)

Se enviaron cuerpos inválidos para verificar el formato unificado de error de la API: { status, message, code, details }.

4.1 Especialidad no válida (Title Case)

  • POST /turnos con especialidad: "PEDIATRÍA" → 400 VALIDATION_ERROR.
{ "status": 400, "message": "Error de validación en los datos ingresados.", "code": "VALIDATION_ERROR", "details": [ { "path": "especialidad", "message": "La especialidad debe estar en formato Title Case (ej. \"Clínica médica\", \"Pediatría\")." } ] }

4.2 Campos faltantes o tipo incorrecto

  • POST /medicos con datos inválidos → 400 VALIDATION_ERROR con details.
{ "status": 400, "message": "Error de validación en los datos ingresados.", "code": "VALIDATION_ERROR", "details": [] }

4.3 Recurso inexistente (404 NOT_FOUND)

  • GET /turnos/99999 → 404 con code NOT_FOUND y formato estándar.
{ "status": 404, "message": "Turno no encontrado.", "code": "NOT_FOUND", "details": [] }

5. Evidencia de consultas con Query Params

5.1 Filtros en Turnos

  • GET /turnos?especialidad=Pediatria → turnos de Pediatría (insensible a mayúsculas/acentos).
  • GET /turnos?medicoId=202 → turnos del médico 202.
GET /turnos?especialidad=Pediatria → [ { "id": 102, "paciente": "Carlos Ruiz", "especialidad": "Pediatría", ... } ]\nGET /turnos?medicoId=202 → [ { "id": 103, "paciente": "Ana Gomez", "especialidad": "Clínica Médica", "medicoId": 202, ... } ]

5.2 Filtros en Médicos

  • GET /medicos?disponible=true → médicos activos.
  • GET /medicos?especialidad=Odontologia&disponible=false → combinación de filtros.
GET /medicos?disponible=true → [ { "id": 202, "nombre": "Dr. Martin Lopez", "activo": true }, ... ]\nGET /medicos?especialidad=Odontologia&disponible=false → [ { "id": 203, "nombre": "Dra. Silvia Rodriguez", "especialidad": "Odontología", "activo": false } ]

7. Evidencia de Mock Server

Se simuló la API localmente con json-server (los datos están normalizados en el archivo postman/mock-db.json con formato de objeto, donde cada clave define un endpoint). Así puede responderse la API sin necesidad del backend real.

7.1 Levantar el Mock Server

npx json-server postman/mock-db.json --port 3001
  • Responderá en http://localhost:3001 con las rutas /turnos y /medicos.
  • Truco: funciona con un archivo de objeto { "turnos": [...], "medicos": [...] } (un archivo con array suelto genera 404 en json-server v1).

7.2 Petición contra el Mock (GET /turnos)

  • Petición: GET http://localhost:3001/turnos en Thunder Client → respuesta simulada 200.

7.3 Otras peticiones contra el Mock

  • GET http://localhost:3001/medicos y GET http://localhost:3001/turnos/99999 (404 simulado).
  • POST /turnos (201), PUT /medicos/:id (200) y DELETE /turnos/:id (200).

8. Conclusión

La API de TurnosRed cumple con los requisitos RESTful solicitados (verbos HTTP correctos y códigos 200/201/204/400/404/500), expone errores bajo un formato estándar unificado, valida los datos con Zod (incluyendo especialidades en Title Case y documento como string), soporta filtros por query params en la capa de servicios, cuenta con tests automatizados en verde y puede simularse localmente mediante un Mock Server de json-server.
